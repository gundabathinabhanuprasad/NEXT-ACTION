# NextAction — Backup, Recovery & Disaster Readiness Guide

## 1. Executive Summary

NextAction's primary operational persistence layer is PostgreSQL 16. This guide details operational backup protocols, logical and physical backup recommendations, disaster recovery procedures, schema migration alignment, recovery point objectives (RPO/RTO), and long-term data retention strategies.

---

## 2. Recovery Objectives

| Metric | Target | Rationale |
| :--- | :--- | :--- |
| **Recovery Point Objective (RPO)** | **< 15 minutes** | Logical snapshots daily + continuous PostgreSQL Write-Ahead Logging (WAL) archiving in production. |
| **Recovery Time Objective (RTO)** | **< 30 minutes** | Standard logical database restore from custom compressed archive (`pg_restore -F c`). |

---

## 3. Data Classification & Criticality

| Category | Database Tables / Entities | Criticality | Recovery Strategy |
| :--- | :--- | :--- | :--- |
| **Core Operational Data** | `users`, `clients`, `workflows`, `tasks`, `task_history`, `user_settings` | **CRITICAL** | Must be fully backed up and restored with zero data loss. Required for business continuity. |
| **Scheduling Entities** | `reminders`, `follow_ups`, `task_templates`, `recurring_tasks` | **HIGH** | Required to preserve pending follow-ups and automated recurring schedules. |
| **Transient Notifications** | `notifications` | **MEDIUM** | In-app notification queue. In a disaster recovery scenario, unread notifications can be reconstructed or re-evaluated via the Phase 19 idempotent scheduler. |
| **Transient & Cached Metrics** | Dashboard KPI aggregates, export CSV/JSON buffers | **LOW** | Computed dynamically on-demand from operational records; zero backup requirement. |

## 4. Logical Backup Procedures

### 4.1 Recommended Backup Command (`pg_dump`)
The recommended logical backup format is PostgreSQL's Custom Format (`-F c`), which is automatically zlib-compressed, allows parallel multithreaded restores, and supports granular object selection.

```bash
# Standard logical backup command
pg_dump \
  -h localhost \
  -p 5432 \
  -U nextaction \
  -F c \
  -b \
  -v \
  -f "/var/backups/nextaction/nextaction_backup_$(date -u +%Y%m%d_%H%M%SZ).dump" \
  nextaction
```

### 4.2 Automated Python Backup Script
A standardized operational utility is provided at `backend/scripts/backup_db.py`:

```bash
# Dry run: view generated commands
python backend/scripts/backup_db.py --dry-run

# Execute backup to destination folder
python backend/scripts/backup_db.py --dest ./backups
```

## 5. Restoration Procedures

### 5.1 Restoring to a Fresh or Staging Database
Before applying a restore to a production instance, always restore to a temporary verification database:

```bash
# 1. Create a clean temporary validation database
createdb -h localhost -p 5432 -U nextaction nextaction_restore_test

# 2. Execute pg_restore with clean object drops and IF EXISTS safeguards
pg_restore \
  -h localhost \
  -p 5432 \
  -U nextaction \
  -d nextaction_restore_test \
  --clean \
  --if-exists \
  --no-owner \
  --no-privileges \
  -v \
  "/var/backups/nextaction/nextaction_backup_20260929_163000Z.dump"

# 3. Verify database connectivity & record counts
psql -h localhost -U nextaction -d nextaction_restore_test -c "SELECT COUNT(*) FROM tasks;"
psql -h localhost -U nextaction -d nextaction_restore_test -c "SELECT COUNT(*) FROM users;"
```

### 5.2 Schema Migration Verification Post-Restore
Following any database restoration, verify that Alembic migration head matches the restored schema:

```bash
cd backend
python -m alembic current
python -m alembic heads
```
*Current expected single head:* `a1b2c3d4e5f6 (head)`

## 6. Backup Verification Protocol

Automated backups that are not tested for restoration are not dependable. The following verification regimen is required:

1. **Weekly Automated Restore Drill**: A scheduled cron or CI pipeline restores the latest backup into an ephemeral PostgreSQL container.
2. **Schema Health Check**: Runs `alembic current` to ensure the restored database matches the canonical migration head without errors.
3. **Data Integrity Ping**: Runs test queries validating foreign key relationships and index viability.
4. **File Size & Checksum Monitoring**: Backups failing size thresholds (< 100 KB) or corrupted hashes immediately trigger operational alerts.

## 7. Data Retention & Archival Strategy

As the NextAction system scales, historical tables will expand at predictable rates:

| Table | Growth Drivers | Retention Policy Recommendation |
| :--- | :--- | :--- |
| `task_history` | Written on every status, priority, attempt, and assignment mutation | Retain permanently for regulatory and audit compliance. Partition by calendar year once table exceeds 5,000,000 rows. |
| `notifications` | Generated by user assignments, mentions, and Phase 19 scheduler runs | Retain read notifications for **90 days**. Purge or archive read notifications older than 90 days via monthly maintenance job. |
| `reminders` | Completed / dismissed reminders | Retain dismissed reminders for **180 days**; preserve active/scheduled reminders indefinitely. |
| `follow_ups` | Completed customer follow-ups | Retain completed follow-ups for **365 days**; linked to task history audit log. |

### Supporting Indexes for Scaled Performance
All high-growth tables feature targeted composite and partial indexes:
- `uq_notifications_user_dedup` (Phase 19 partial index preventing duplicate notifications)
- `idx_notifications_user_read` (Indexed on `(user_id, is_read)` for instant unread count lookups)
- `idx_tasks_created_at`, `idx_tasks_priority`, `idx_tasks_due_date` (Phase 13 query indexes)
- `idx_task_history_task_id` (Instant task audit history traversal)
